# Design Decisions

Log of notable decisions: what was decided, alternatives considered, and why. Marked as **[owner: assistant]** for boilerplate/infra calls made per CLAUDE.md, or **[owner: user]** for calls in the assist-only areas (tool/resource modeling, auth design, whitelist content, data/instruction boundaries, single/multi-user scope).

## S1 — Repository scaffold, `list_courses`

### 2026-08-13 — Package manager: uv **[owner: assistant]**
- **Decision:** Use `uv` with a standard PEP 621 `pyproject.toml`, mirroring the sister project `studylife-ai`.
- **Why:** Already installed locally, fast, standard `pyproject.toml` rather than a tool-specific lockfile format.

### 2026-08-13 — src-layout **[owner: assistant]**
- **Decision:** Application code lives under `src/studylife_mcp/`, not a flat top-level package.
- **Why:** Standard practice for installable Python packages; prevents accidentally importing the working-tree copy instead of the installed package during tests.

### 2026-08-13 — MCP Python SDK: latest (2.0, `MCPServer`) instead of pinning to the pre-2.0 `FastMCP` API **[owner: user]**
- **Decision:** Depend on `mcp>=2.0`. The 2.0 release renamed/restructured the ergonomic server API: `mcp.server.fastmcp.FastMCP` → `mcp.server.mcpserver.MCPServer`. CLAUDE.md's architecture line names "FastMCP" specifically (written before 2.0 existed).
- **Alternatives:** Pin `mcp>=1.9,<2.0` to stay on the exact API CLAUDE.md names and that this assistant has solid prior knowledge of, revisiting the SDK version as its own explicit decision later.
- **Why:** User explicitly asked to be on the current, state-of-the-art SDK version rather than pinned to what was already known. The 2.0 `MCPServer` API is a near-drop-in replacement for the same usage pattern this project needs (`@mcp.tool()` decorator, `mcp.run()` defaulting to stdio) — confirmed by reading the installed package's source directly rather than assuming API compatibility.

### 2026-08-13 — `Course` DTO shape read from the `studylife` source, not assumed **[owner: assistant, per CLAUDE.md "kein Swagger, nachfragen" — resolved by reading the local sibling repo]**
- **Decision:** `models.Course` mirrors `StudyLife.Shared.CourseDto` exactly (`src/StudyLife.Shared/CourseCatalog.cs` in the `studylife` repo): `id, semester, name, code, color, icon, topics, ects, group`. Field names match as-is — ASP.NET Core's default `System.Text.Json` camelCase policy applies (confirmed: no `AddJsonOptions`/`JsonNamingPolicy` override in `Program.cs`), and every `CourseDto` field is already a single word, so camelCase and Pydantic's snake_case coincide with no aliasing needed.
- **Why:** CLAUDE.md forbids assuming endpoint/DTO shapes not in the documented prior knowledge. The `studylife` repo happens to be checked out locally as a sibling project, so the actual controller (`CoursesController.GetAll`) and DTO were read directly instead of guessing or asking the user to paste them.

### 2026-08-13 — Auth for S1: reuse the existing Home-Assistant API-key slot (`ApiKeyHash`) **[owner: user]**
- **Decision:** `STUDYLIFE_API_KEY` for local dev is a key from the existing HA slot, not a new dedicated `McpApiKeyHash` slot.
- **Why:** User's call, pragmatic for S1. Confirmed in `studylife`'s API-gate middleware (`Program.cs`) that both `ApiKeyHash` and `AiApiKeyHash` authenticate identically against `X-Api-Key` — reusing the HA slot works with zero StudyLife-side changes. The dedicated-slot-vs-reuse question (per CLAUDE.md's "Auth-Design" assist-only area, precedent: `studylife-ai`'s "Dedicated StudyLife API key" decision) is deferred, to be revisited explicitly before S3 (write tools raise the stakes of slot reuse).

### 2026-08-13 — TLS trust: OS certificate store via `truststore`, not disabled verification **[owner: assistant, confirmed by user's dev-cert trust]**
- **Decision:** `StudyLifeClient` verifies TLS using `truststore.SSLContext` (OS certificate store) instead of `httpx`'s default `certifi` bundle, and instead of `verify=False`.
- **Why:** The local StudyLife dev instance runs on `https://localhost:53963/` with the ASP.NET Core HTTPS dev certificate. `certifi` doesn't know about locally-trusted dev certs; user confirmed (`Get-ChildItem Cert:\CurrentUser\Root`) the cert is already registered via `dotnet dev-certs https --trust`. Using the OS store keeps real certificate validation intact rather than disabling it, which CLAUDE.md's security posture (destructive/insecure shortcuts only when explicitly instructed) argues against.

### 2026-08-13 — `.env` holds real local-dev credentials, is gitignored **[owner: user]**
- **Decision:** Local `.env` contains the actual `STUDYLIFE_BASE_URL`/`STUDYLIFE_API_KEY` for the user's dev instance; `.env.example` (tracked) has placeholders only.
- **Why:** Standard secret-hygiene per CLAUDE.md ("keine Secrets in Code/Doku/Tests"); `.gitignore` excludes `.env*` except `.env.example` from the very first commit, before `.env` was written.

### 2026-08-13 — Claude Desktop config location: MSIX-packaged app redirects `%APPDATA%\Claude` **[owner: assistant]**
- **Finding:** On this machine, the "Claude" app is installed as an MSIX-packaged app (package id `Claude_pzs8sxrjxfjjc`), not a traditional installer. Its `%APPDATA%\Claude` is redirected by Windows to `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\`. `claude_desktop_config.json` lives there, confirmed both by reading the app's own logs (`logs\main.log`: `LocalMcpServerManager`/`localMcpBridge`, `configType: "stdio"`) and by the user's Settings → Developer → "Local MCP servers" pointing at the same path.
- **Why documented:** The initial README instructions assumed the classic `%APPDATA%\Claude\claude_desktop_config.json` path, which doesn't exist on this install (only the redirected one does) — worth a note for anyone else setting this up on a similarly MSIX-packaged install, since the standard published docs don't mention the redirect. Also: this app version's "Benutzerdefinierten Connector hinzufügen" UI is remote-URL-only (Streamable HTTP, now S4 scope) — local stdio servers are added exclusively by editing `claude_desktop_config.json` directly, confirmed via Settings → Developer → "Local MCP servers".

## S2 — StudyLife resources read-only

### 2026-08-13 — DTO field shapes verified against `studylife` source, not assumed **[owner: assistant]**
- **Decision:** `Note`, `Session`, `CourseGoal` models mirror `NoteDto`, `StudySessionDto`, `CourseGoalDto` (all in `StudyLife.Shared/Dtos.cs`) field-for-field, read directly from the local sibling `studylife` repo rather than guessed, same approach as `Course` in S1.
- **Notable finding:** `CourseGoalDto.CompletedTopics` is a comma-separated `string` on the wire (default `""`, not nullable), not a JSON array — modeled as `str`, not `list[str]`, to match the actual response shape and avoid a validation crash/silent per-character split.

### 2026-08-13 — camelCase JSON alias generation, added after a real test failure **[owner: assistant]**
- **Decision:** `StudyLifeModel` (new shared base class in `models.py`) sets `model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)`; `Course`, `Note`, `Session`, `CourseGoal` all inherit from it instead of `BaseModel` directly.
- **Why:** ASP.NET Core's default JSON serialization is camelCase. `Course`'s fields are all single words, so its snake_case Python names happened to already match the wire format (`ects` vs `ects`) — this accidentally worked in S1 without any alias handling. `Note`/`Session`/`CourseGoal` have multi-word fields (`courseId`, `createdAt`, `isCompleted`, ...) that do NOT match their snake_case Python names, and this was only caught because the new `respx`-mocked tests used realistic camelCase payloads (`courseId`, not `course_id`) and failed with `pydantic_core.ValidationError: Field required`. Without the alias generator, every field in these three models would have silently landed as `None`/its default instead of erroring, since none of them happen to be fully required-with-no-default — worth flagging as a class of bug this project should keep testing against with real-shaped payloads, not idealized ones.

### 2026-08-13 — S2 modeling decisions **[owner: user]**
- **Tools, not Resources:** `list_notes`, `search_notes`, `list_sessions`, `list_course_goals` are all MCP tools, consistent with `list_courses` from S1 — not MCP resources. Rationale discussed: tool calls are model-driven and universally supported across MCP clients, matching this project's actual usage pattern (the user asking Claude a question, Claude deciding mid-conversation to call a tool) confirmed live in S1. Resources are more for host-app-managed/browsable context and aren't as consistently model-invocable across clients; using them here would mix two MCP concepts without a concrete driving reason.
- **`list_notes` pagination:** none. `GET /api/notes` returns everything server-side already (confirmed, no server pagination); `list_notes` passes all of it through as-is rather than adding a client-side `limit` parameter. Revisit only if a real note collection turns out to be large enough to matter.
- **Progress/ECTS scope:** `list_course_goals` exposes the raw `CourseGoalDto` list only (target date, completion status, grade, completed topics, tag) — no aggregate ECTS total or weighted grade average. That computation only exists today behind `GET /api/progress/shared/{token}` (a separate, token-based auth path, not the normal `X-Api-Key`), which would need a second secret in `.env` to use here; reimplementing `CourseCatalog.CalcTotalEcts`/`CalcEctsEarned`/`StudyMetrics.CalcWeightedAverageGrade` in Python was rejected as unnecessary duplication of backend logic that would need to stay in sync. Revisit if raw course goals prove insufficient for real usage.
- **`search_notes` is its own tool**, not a query parameter folded into `list_notes` — keeps each tool's description and return-shape unambiguous (list everything vs. full-text search).

### 2026-08-13 — Free-text fields flagged as data, not instructions, in tool descriptions **[owner: assistant]**
- **Decision:** `list_notes`, `search_notes`, `list_sessions`, `list_course_goals` docstrings explicitly say the free-text fields they return (note title/content, session topic/notes, course-goal completion note) are user-authored data, not instructions to follow.
- **Why:** CLAUDE.md flags data-vs-instruction boundaries as something to think about from the start, citing studylife-ai's `</notes>`-escaping incident as precedent. That specific incident was about a hand-built XML-style delimiter breaking under injected content — doesn't directly apply here, since MCP tool results are transported as JSON-RPC (each field JSON-string-escaped by the protocol itself, no custom delimiter this project constructs). The remaining, distinct risk — a note's free text attempting to steer Claude's behavior once it's in context — is addressed lightly via the docstring wording rather than heavier mechanisms (e.g. wrapping/escaping content, blocking certain patterns), appropriate for the current single-user scope where the user is also the note author. Revisit if scope ever expands beyond single-user.

### 2026-08-13 — S2 verified end-to-end against the real instance **[owner: assistant]**
- **Verification:** `ruff check`, `ruff format --check`, `mypy --strict src`, `pytest` (15 tests: happy path/401/timeout × 5 client methods) all pass. Beyond mocks: a throwaway script called the real `StudyLifeClient` against the user's live StudyLife instance — `list_notes`, `list_sessions`, `list_course_goals`, and `search_notes` all returned HTTP 200 with empty arrays (confirmed via a raw `httpx` probe printing status + body, not just the parsed/empty Python result) — the user's instance simply has no notes/sessions/course-goals recorded yet. Not a bug: `list_courses` already proved auth/TLS/parsing work end-to-end in S1, and every new endpoint responded correctly, just with no data.

### 2026-08-13 — Pushed S2 in 5 small commits, CI green **[owner: assistant, per user instruction]**
- models → client → server → tests → docs, each its own commit (Conventional Commits, per CLAUDE.md). Pushed; GitHub Actions `lint` and `test` jobs both passed on the resulting `main`.

## S3 — Write tools: `create_note`, `create_session`

### 2026-08-13 — Auth: dedicated `McpApiKeyHash` key slot, not the shared HA key **[owner: user]**
- **Decision:** Now that S3 introduces write access, StudyLife gets a third API-key slot, `McpApiKeyHash`, mirroring the existing `AiApiKeyHash` pattern (added 2026-08-10 for `studylife-ai`, for the identical blast-radius reason) instead of continuing to reuse the Home Assistant key (`ApiKeyHash`) from S1.
- **Why:** Precedent already established in `studylife-ai/docs/decisions.md` ("Dedicated StudyLife API key" — a shared credential across unrelated integrations is a real credential-hygiene/blast-radius issue, not just untidy) — the same reasoning applies here, more so once writes are involved. Home Assistant's own key already performs writes against StudyLife on its own (e.g. the `generate_exam_plan` service) — sharing that credential with `studylife-mcp`'s writes would make it impossible to tell which system wrote what, or to revoke one without affecting the other.
- **Where the change lives:** entirely in the separate `studylife` repo (Blazor + ASP.NET Core, not this Python project) — mirrors `AiApiKeyHash` layer-for-layer: `AuthUserEntity.McpApiKeyHash`, EF migrations for both SQLite and Postgres, `api/settings/mcp-api-key` controller endpoints, a new setup-page card, and translations across all 26 supported languages. Implemented by a background agent on branch `feat/mcp-api-key`, reviewed and merged by the user (PR #2, commit `90273c7`) into `studylife`'s `main`. `.env` here now holds a real key generated via the new setup card against the local dev instance; confirmed working via a read-only `list_courses` call (58 courses visible) before any write tool was exercised.

### 2026-08-13 — Claude Desktop config: `uv run --no-sync`, to stop a restart-time race **[owner: assistant]**
- **Decision:** Added `--no-sync` to the `studylife` entry's `args` in `claude_desktop_config.json` (see the S1 decision on this file's actual location on this machine).
- **Why:** After updating `.env` with the new key, restarting Claude Desktop failed once (`mcp-server-studylife.log`: `error: failed to remove directory ...studylife_mcp-0.1.0.dist-info: Zugriff verweigert (os error 5)`, then `Server transport closed unexpectedly`). Root cause: `uv run` re-syncs the project on every launch by default; the just-killed previous server process hadn't fully released its lock on the venv's `dist-info` yet, so the sync step failed and aborted the launch before the Python entrypoint even started — the exact same class of Windows/OneDrive file-lock issue hit repeatedly during this project's own development (worked around there with `uv run --no-sync` too, see the S2/S3 verification notes). The app auto-retried a few seconds later and succeeded once the lock cleared, but that's not something to rely on. Since dependencies are only ever synced explicitly during development (`uv sync` after any `pyproject.toml` change), the running server never needs a fresh sync at launch — `--no-sync` removes the race entirely rather than hoping the timing works out.

### 2026-08-13 — Write-tool confirmation: Claude's client-side tool-approval only, no server-side confirm step **[owner: user]**
- **Decision:** `create_note`/`create_session` rely entirely on the MCP client's own tool-approval prompt (Claude Desktop asks for confirmation before running a tool by default) — no server-side propose→confirm flow (unlike `studylife-ai`'s M4 agent, which pauses its LangGraph execution via `HumanInTheLoopMiddleware` before a write).
- **Why:** Matches this project's stated architecture — "kein eigener Agent-Loop, der MCP-Client ist der Agent" (CLAUDE.md) — building a second confirmation mechanism here would duplicate what the client already owns, for a single-user local stdio server where that client-side prompt is the actual, present safety net. Revisit only if this server ever runs unattended (e.g. behind the planned S4 HTTP transport with a client that doesn't prompt).

### 2026-08-13 — Whitelist enforcement: the tool surface itself is the whitelist **[owner: assistant]**
- **Decision:** No separate runtime whitelist/allowlist check was added. `create_note` and `create_session` are the only two write-capable functions that exist at all in `server.py` — there is no generic "call this StudyLife endpoint" tool, no update/delete tool, not even commented out.
- **Why:** CLAUDE.md requires "keine Update-/Delete-Tools... ausgeschlossen, nicht nur unimplementiert" — a fixed, closed set of Python functions already satisfies that; a separate whitelist-checking layer would be redundant indirection for something structurally already true.

### 2026-08-13 — Audit log: structured, stderr-only, digests not raw values **[owner: assistant]**
- **Decision:** New `audit.py` provides an `@audited(tool_name)` decorator applied to every tool (read and write), logging `tool`, a truncated SHA-256 digest of the call's arguments, `result` (`ok`/`error`), and `duration_ms` via the standard `logging` module to **stderr** (never stdout, which carries the stdio JSON-RPC transport and would be corrupted by any stray write).
- **Why:** CLAUDE.md's fixed architecture line specifies exactly this shape ("Tool, Args-Digest, Ergebnis, Dauer") for every tool call, not just writes (the narrower "Sicherheit" row wording, "Audit-Log jeder Schreibaktion", is satisfied as a subset). Digesting rather than logging raw arguments matters concretely here: `create_note`/`create_session` arguments include user free text (title, content, topic, notes) that shouldn't land in a log file just because a tool was called.

### 2026-08-13 — `create_session`/`create_note` request shape: minimal payload, not the full DTO **[owner: assistant]**
- **Decision:** `StudyLifeClient.create_note`/`create_session` build a small hand-written dict for the POST body (title/content/courseId/sessionId; courseId/courseName/courseColor/startTime/endTime/topic/notes/isCompleted/timerModeId) instead of constructing a full `Note`/`Session` model instance with placeholder values for server-assigned fields (`id`, `createdAt`, `updatedAt`) that StudyLife ignores/overwrites on create anyway (confirmed in `NotesController.Create`/`SessionsController.Create`).
- **`timer_mode_id` defaults to `1`** when not given — matches the exact fallback `PlannerController`'s own server-side session creation (`GenerateExamPlan`) uses when there's no interactive timer selection, so this isn't an invented default.
- **`create_session` exposes `is_completed`** (default `False`) so a session can be logged retroactively ("I just studied for 2 hours") as well as scheduled ahead — a real, plausible use case for a study-tracking tool, not speculative.

### 2026-08-13 — `StudyLifeClient` refactored onto a shared `_request` helper, improving error messages **[owner: assistant]**
- **Decision:** All client methods now route through a private `_request(method, path, **kwargs)` that raises `httpx.HTTPStatusError` with the response body included in the message, instead of each method calling `response.raise_for_status()` (whose message omits the body).
- **Why:** Found while adding the write tools: StudyLife's write validation (`SessionsController.Validate`) returns its actual error as the response body (e.g. "EndTime must be after StartTime.") via `BadRequest(error)` — `raise_for_status()` alone would only surface a generic "400 Bad Request", losing exactly the information the calling LLM needs to correct a bad write and retry. Applied to all methods, not just the new write ones, both for consistency and because the same information loss existed silently in every S1/S2 read method too.

### 2026-08-13 — S3 verified end-to-end, live in Claude Desktop, against the real instance **[owner: assistant/user]**
- **Verification:** After the `McpApiKeyHash` slot went live (S1 decision above) and Claude Desktop was restarted, the user exercised `create_note` and `create_session` directly through the live app — the client-side tool-approval prompt (the S3 confirmation-semantics decision above) fired as expected, and both writes succeeded. Confirmed independently with a read-only follow-up (`list_notes`/`list_sessions` called directly, not through the app): exactly one note (`"Suchalgorithmen: Uninformierte vs. Informierte Suche"`, correctly linked to `course_id=1`) and one session (`"Artificial Intelligence"`, 2026-08-14 16:00–21:00, `is_completed=False`) — both with correctly parsed `datetime` fields, confirming the camelCase alias handling and datetime typing work against real StudyLife responses, not just the mocked test payloads.
- **S3 Definition of Done (per CLAUDE.md): met.**

## S4 — Streamable HTTP transport, OAuth 2.1, multi-user, Docker, MCP Inspector

### 2026-08-13 — HTTP transport is real deployment (own reverse proxy/TLS), auth is spec-conformant OAuth 2.1 **[owner: user]**
- **Decision:** S4's HTTP transport isn't a localhost-only Inspector convenience — it's meant to run on the user's own cluster (existing TLS/reverse proxy), reachable as a real remote MCP connector (the "Custom Connector" URL flow found during the Claude-app research earlier this project). Auth is full OAuth 2.1 (authorization code + PKCE, dynamic client registration), not a shared static bearer token.
- **Why:** User's explicit call, citing this project's portfolio purpose — a shared-secret token would have been far less work, but wouldn't demonstrate the MCP spec's actual recommended remote-auth story.

### 2026-08-13 — This server is a self-built OAuth Authorization Server, architected to later delegate to an external IdP **[owner: user]**
- **Decision:** `studylife-mcp` implements its own `OAuthAuthorizationServerProvider` (`oauth_provider.py`) rather than only being a Resource Server against an existing IdP (Authentik/Keycloak/etc.) — the user doesn't have one running yet. Deliberately split so that becomes a small, later swap: `StudyLifeOAuthProvider.authorize()` is the *only* place that decides how the resource owner logs in, and currently returns a URL to this server's own login page (`register_oauth_routes`) rather than to a third-party IdP. Federating later means changing what `authorize()` redirects to (and adding a callback route), not touching `load_authorization_code`/`exchange_authorization_code`/token issuance/`revoke_token` at all.
- **Why:** The MCP auth spec itself models exactly this shape — `authorize()`'s own docstring describes the "AS redirects to a third-party OAuth server, then handles the return leg" pattern as a first-class case. Building a full custom AS is real security-sensitive surface area (the SDK provides the HTTP handlers and PKCE/expiry/redirect-URI verification, but client storage, code/token issuance, and the actual login step are this project's own code) — worth flagging plainly rather than glossing over, and exactly why the split matters: today's login step (a password-equivalent, see next entry) is the smallest, most replaceable part of the whole thing.

### 2026-08-13 — Multi-user: the login step *is* the per-user StudyLife account link **[owner: user]**
- **Decision:** The OAuth login page (`GET`/`POST /login`) doesn't ask for a generic username/password — it asks the caller to paste their own StudyLife MCP API key (the same key from StudyLife's "StudyLife MCP Server" setup card, S3). The submitted key is validated against StudyLife directly (`StudyLifeClient(...).list_courses()`; a 401 means an invalid key) and then becomes the OAuth `subject` (`OAuthStore.subject_for_key`: a SHA-256 hash of the key, not the key itself) that every access/refresh token issued from that login carries. At tool-call time, `client_resolver.StudyLifeClientResolver` resolves the caller's access token back to their own StudyLife account.
- **Why:** StudyLife is itself multi-user, and each user already has their own independent `McpApiKeyHash` key (S3) — reusing that as the login credential means zero new StudyLife-side work, and it composes with the existing per-integration blast-radius design instead of inventing a parallel identity system. Two or more StudyLife users can point their own MCP client at the same `studylife-mcp` deployment and each only ever sees/writes their own data — confirmed live (see the verification entry below).
- **`.env`'s `STUDYLIFE_API_KEY` remains the stdio-mode account only.** HTTP+OAuth mode never falls back to it for an authenticated caller — `StudyLifeClientResolver` fails closed (`PermissionError`) if a token's subject has no stored key, rather than silently serving the `.env` account's data to an unrelated caller.

### 2026-08-13 — OAuth store: SQLite, encrypted-at-rest StudyLife keys, connection-per-call **[owner: assistant]**
- **Decision:** `oauth_store.py`'s `OAuthStore` persists registered clients, pending-authorization bridges, authorization codes, access/refresh tokens, and per-subject StudyLife keys in SQLite (`aiosqlite`, WAL mode), one file (`MCP_OAUTH_DB_PATH`, default `oauth.db`, gitignored). Every other row type stores pydantic models as JSON blobs directly (`model_dump_json()`/`model_validate_json()`) rather than hand-mapped columns — the SDK's own `AuthorizationCode`/`AccessToken`/`RefreshToken`/`OAuthClientInformationFull` types are already the right shape. StudyLife keys are the one exception: encrypted with `cryptography.fernet.Fernet` (`MCP_TOKEN_ENCRYPTION_KEY`, a new required-for-HTTP-mode secret) rather than hashed, because unlike StudyLife's own key storage, this server must get the plaintext back to call StudyLife on the user's behalf.
- **Opens a fresh connection per call rather than one held open for the process lifetime** — simpler to reason about/test at this traffic scale (personal/small-multi-user deployment); revisit only if that stops being true.
- **Bug found and fixed during testing:** the first version wrote `async with await self._connect() as conn:` everywhere, awaiting `aiosqlite.connect()`'s result (which starts its background thread) and then entering `async with` on the *same* already-awaited connection object — `Connection.__aenter__` awaits it again, tries to start the same thread a second time, and raises `RuntimeError: threads can only be started once`. Fixed with a proper `@asynccontextmanager _connection()` that awaits exactly once. Caught immediately by the very first `oauth_store` test run — worth noting as a concrete case for why "write the tests" isn't optional busywork here.

### 2026-08-13 — `client_resolver.py` split out of `server.py` for testability **[owner: assistant]**
- **Decision:** The "which StudyLife account does this tool call run against" logic lives in its own `StudyLifeClientResolver` class (constructor-injected `Settings`/`OAuthStore`), not as free functions closing over `server.py`'s module-level globals.
- **Why:** `server.py` calls `Settings()` from the real environment at *import time* (existing S1 pattern) — any test importing `server.py` directly would need a real `.env`, which doesn't exist in CI. Extracting the resolver into a class that takes its dependencies as constructor arguments makes it fully testable in isolation (`tests/test_client_resolver.py`) without importing `server.py` at all, and is better design regardless (no mutable module-level global dict of per-subject clients).

### 2026-08-13 — Tools stay unchanged; per-request identity comes from a contextvar, not a `Context` parameter **[owner: assistant]**
- **Finding:** The SDK's `get_access_token()` (`mcp.server.auth.middleware.auth_context`) reads from a contextvar set by `AuthContextMiddleware` during HTTP request handling — callable from anywhere during a request without needing a `Context` object threaded through the tool function's signature. Outside a request (stdio, or an unauthenticated HTTP call) it just returns `None`. ### 2026-08-13 — Rate limit + TTL cleanup for dynamic client registration **[owner: user]**
- **Decision:** Before exposing the server publicly, hardened the previously-unrestricted RFC 7591 `/register` endpoint two ways: `rate_limit.py`'s `RegistrationRateLimitMiddleware` caps registrations to 5/hour per source IP (read from `X-Forwarded-For` when present, else the direct connection) with a 429 response once exceeded; `oauth_store.py`'s `register_client()` opportunistically purges any client that registered but never completed the OAuth flow (no access token ever issued — tracked via a new `activated_at` column, set once by `save_access_token()`) after `UNUSED_CLIENT_TTL_SECONDS` (24h), run on every new registration rather than a separate background job.
- **Why:** `/register` has no authentication by protocol design (any MCP client self-registers) — fine on a home-network-only deployment, but once publicly reachable it's a free, repeatable action for any bot/scanner. Real data access was never at risk through this endpoint (every tool call still requires a real StudyLife API key at `/login`), so this closes a storage-growth/abuse-surface gap, not a data-access hole. Rejected as insufficient alone: a hard cap on total registered clients (crude — bots filling it could block the user's own next real registration); rejected as disproportionate for now: a pre-shared initial-access-token gate on `/register` (RFC 7591's own mechanism for this, but breaks the zero-config registration flow real MCP clients expect, with no confirmed way to make Claude Desktop send it).
- **Scope note:** the `X-Forwarded-For`-based IP is not a security boundary (a caller could spoof it) — this only needs to slow casual scanning, not resist a targeted attacker, consistent with the previous entry's risk framing.
- **Verified:** `ruff`, `mypy --strict`, and `pytest` (63 tests: the existing 56 plus 4 new rate-limit tests and 2 new TTL-cleanup tests plus one existing-test-format tweak) all pass.

### 2026-08-13 — Tailscale Funnel: public exposure scoped to exactly one service, enforced by the tailnet ACL **[owner: user]**
- **Decision:** `studylife-mcp` is now publicly reachable at its tailnet-assigned MagicDNS Funnel hostname (not written out in this public repo on purpose) via the Tailscale Kubernetes operator (Helm-installed into a new `tailscale` namespace) and `k8s/07-tailscale-funnel.yaml`, an `Ingress` (`ingressClassName: tailscale`) annotated `tailscale.com/funnel: "true"` and `tailscale.com/tags: "tag:studylife-mcp-funnel"`.
- **Why the dedicated tag, not the operator's default `tag:k8s`:** the user's explicit requirement was that *only* the MCP server may ever be public, everything else stays tailnet/LAN-only. Any future Ingress would default to `tag:k8s`, which the ACL does not grant Funnel to - so exposing it publicly would require a second, deliberate ACL change, not just one annotation. This is enforced by the tailnet policy itself, not by convention/care alone.
- **Cluster-side plumbing:** the operator's ingress proxy runs as a StatefulSet in its own `tailscale` namespace (not `studylife-mcp`), so `k8s/05-network-policies.yaml` gained `allow-tailscale-to-studylife-mcp`, mirroring the existing `allow-nginx-gateway-to-studylife-mcp` pattern. - **OAuth client secret handling:** the Tailscale operator's OAuth client credentials (`operator-oauth` Secret, `tailscale` namespace) were created directly by the user via `kubectl create secret` in their own terminal - never pasted into or applied through the assistant, since this credential grants tailnet-wide device-management authority (a materially larger blast radius than any single app's own API key).

- **What happened:** the `studylife` repo's `k8s/07c-gateway.yaml` (a single shared Gateway resource serving StudyLife, Grafana, Uptime Kuma, piwatch, homelab-hub, and studylife-mcp) had drifted - the live object's listener hostnames were `*.heim.lan`/a real domain, but the git file still said `*.home.lan`/`example.com` for every listener. When `studylife-mcp-heim` was added earlier, only the two new listener entries were written correctly; the file's other 12 entries were left as-is, reasoning "leave the pre-existing drift on the others untouched." That reasoning was wrong for a resource `kubectl apply -f` re-applies in full: applying the file didn't just add the new listeners, it also silently reverted every other listener's hostname back to the stale value. Gateway API only binds an HTTPRoute to a listener when their hostnames intersect - `home.lan` listeners and the actual `heim.lan` HTTPRoutes shared no intersection, so every route lost its "Accepted" status (`NotAllowedByListeners`) and every one of those five other services went unreachable (TLS handshake failure, not even a proper HTTP error). Not caught immediately because only `studylife-mcp`'s own reachability was tested after each Gateway edit, never the other services sharing the same resource.
- **Fix:** rewrote every hostname in `k8s/07c-gateway.yaml` to match what was actually live (`heim.lan`/the real domain throughout), applied immediately to restore service, then committed/pushed so the file itself is no longer a live landmine.
- **The actual lesson, stated plainly:** for a Kubernetes resource where `kubectl apply` replaces the object wholesale, "only touch the part I care about, leave the rest of the file as found" is not a safe strategy if the file doesn't already match live reality - either reconcile the whole file to live state first, or don't `kubectl apply` it at all until it does. This was flagged as a known discrepancy in an earlier entry and left unaddressed specifically because fixing it felt out of scope - it should have been treated as a blocking prerequisite before touching that file again, not a deferrable cleanup.

### 2026-08-13 — Real-world dashboard testing found: `rate()`/`increase()` extrapolation confusion, plus a new registered-clients gauge **[owner: user]**
- **What happened:** live-testing the new dashboard, single tool calls and rate-limit rejections showed `0` (or a non-integer like `1.04`) on panels using `rate()`/`increase()`, even though the underlying counter and the independent audit log both confirmed the event happened exactly once. Root cause in each case: `rate()`/`increase()` measure *change observed within the query window*, not the absolute value - a counter whose only sample(s) so far all show the same value (nothing rose during Prometheus's own observation history) legitimately evaluates to `0`, and low-sample-count counters are documented to extrapolate to non-integer results. Confirmed via `query_range` showing a flat, unchanging value across the whole window in both cases - not a bug in the app, the metric, or the dashboard.
- **New metric added along the way:** `studylife_mcp_registered_clients{status="activated"|"pending"}` (`metrics.py`, a `Gauge`) and `OAuthStore.count_clients_by_status()` (`oauth_store.py`) - queried fresh from the database on every `/metrics` scrape (not tracked incrementally in-process, so it can never drift from the real table, including whatever the TTL cleanup just removed). Requested live: a direct, ongoing signal for whether the DCR rate-limit/TTL-cleanup pair (see the two entries above) is actually keeping `pending` bounded under real traffic, not just that the mechanism exists - specifically so the next day's natural TTL cleanup of the manual rate-limit-test registrations would be visible on the dashboard rather than invisible.
- **Verified:** 2 new `OAuthStore` tests (empty store, mixed activated/pending counts), 89 tests total; a new "Registrierte OAuth-Clients" panel added to the Grafana dashboard (`studylife` repo's `k8s/17b-grafana-dashboards.yaml`).

### 2026-08-14 — Loki/Promtail actually deployed; two unrelated deploy bugs found and fixed **[owner: user]**
- **What happened:** `k8s/18-loki.yaml` and `k8s/19-promtail.yaml` (`studylife` repo) had existed in git for a while but were never actually running - asked to get them working for real rather than assumed-working from the manifests alone.
- **Bug 1 - Promtail's `kubernetes_sd_configs` silently produced zero targets:** the original scrape config (`role: pod`, relabeling `__meta_kubernetes_pod_uid` into a glob `__path__`) never discovered a single log file - `promtail_targets_active_total` stayed `0` forever, debug logs stopped dead after `"Starting provider"` with nothing further. Ruled out RBAC and TLS specifically: raw `LIST`/`WATCH` calls against the API server using the exact same ServiceAccount token worked instantly, with and without certificate validation. Root cause not fully identified - looks like a genuine incompatibility between this Promtail version's K8s SD client and this specific K3s API server. Worked around instead of chased further: rewrote `scrape_configs` to a `static_configs` glob (`/var/log/pods/*/*/*.log`) plus a `pipeline_stages` `regex`/`labels` pair that extracts `namespace`/`pod`/`container` straight from the hostPath file path (`filename` is auto-populated per matched file) - needs zero Kubernetes API access, so the `promtail` ServiceAccount/ClusterRole/ClusterRoleBinding were deleted entirely.
- **Bug 2 - `monitoring`'s default-deny-ingress NetworkPolicy had no `allow-ingress-to-loki` rule** (every other service in that namespace has its own) - pushes failed with connection refused regardless of bug 1. Fixed by adding one (`k8s/12-network-policies.yaml`), mirroring the existing `allow-ingress-to-prometheus` rule, allowing both `promtail` (pushes) and `grafana` (Explore queries).
- **Bug 3 - after fixing both of the above, the DaemonSet still failed to roll out** (`FailedCreate: serviceaccount "promtail" not found`) even though the applied manifest no longer references a `serviceAccountName` at all. Cause: that field was never tracked by `kubectl apply`'s three-way merge in the first place (absent from `last-applied-configuration`, most likely because the object's very first deploy wasn't done via `apply`), so removing it from the file did nothing live - `apply` only clears a field it remembers setting. Fixed by deleting the DaemonSet object outright and re-`apply`-ing the file fresh (the ConfigMap was untouched). Generalizes the same lesson as the shared-Gateway incident above: `apply`'s diff is relative to what it *remembers* changing, not relative to the full live object - a field that pre-dates the first `apply` can be invisible to it indefinitely.
- **Verified end-to-end, not just "pods are Running":** both Promtail pods (one per node) show `promtail_targets_active_total 1` and `promtail_dropped_entries_total 0` across every reason label; queried Loki directly (`/loki/api/v1/query_range`) and got back real `studylife-mcp` log lines with correctly parsed `namespace`/`pod`/`container` labels - the same API/labels Grafana Explore's pre-configured Loki datasource uses.

### 2026-08-14 — Expired-client cleanup is now periodic, not just opportunistic **[owner: user]**
- **What happened:** live-checked the `studylife_mcp_registered_clients{status="pending"}` dashboard gauge roughly 24h after some manual rate-limit testing (see the two entries above) - still showed 6, expected 0. Cause: `register_client()`'s TTL sweep only ever ran on the *next* registration, and nobody had registered a new client since the test - correct-but-stale, not a metric or cleanup bug (confirmed live: all 6 rows in the SQLite `clients` table were genuinely past `UNUSED_CLIENT_TTL_SECONDS`, just never swept because nothing triggered it).
- **Decision:** kept the opportunistic sweep in `register_client()` (still useful - bounds growth exactly when registration spam would cause it) and added a second, independent path: `OAuthStore.run_periodic_cleanup()`, an hourly (`CLEANUP_INTERVAL_SECONDS`) background loop started via `anyio.create_task_group()` alongside the HTTP server in `main_http()` (`server.py`). Extracted the shared `DELETE` into `cleanup_expired_clients()` so both paths call the same code. stdio-only operation is unaffected (`main_http()` is HTTP-transport-only, matching where DCR/OAuth exist at all).
- **Why in-process instead of a separate cron/CronJob:** this server already owns its own lifecycle end-to-end (single container, single process) - a `k8s` CronJob would mean a second entrypoint, its own DB access, its own image invocation, for a task that's cheap enough to just interval-sleep alongside the request loop it's already sharing a process with.
- **Verified:** 3 new `OAuthStore` tests (direct sweep + count, no-op when nothing's expired, and the actual point - an expired client removed via the periodic loop alone with zero registrations happening), 92 tests total; `ruff`/`mypy` clean.

## Round 2 — Identity Contract v1: StudyLife-hosted connect flow

### 2026-08-26 — Login replaced with a StudyLife-hosted connect flow; OAuth subject is now the real user id **[owner: user, spec: identity-contract-v1]**
- **Decision:** `authorize()` no longer redirects to this server's own `/login` form. It redirects the browser to `{STUDYLIFE_CONNECT_URL}/connect/mcp?redirect_uri=...&state=...` - a new StudyLife-hosted page (built by a parallel effort against the same shared spec) that requires a real passkey session and asks for explicit consent, then redirects back to a new route here, `GET /auth/studylife/callback?assertion=...&state=...`. That route exchanges the single-use assertion server-to-server (`POST {STUDYLIFE_BASE_URL}/api/auth/mcp-assertion-exchange`, new `client.exchange_mcp_assertion()`, exempt from the normal `X-Api-Key` gate by design) for `{userId, mcpApiKey}`, stores the key Fernet-encrypted under subject `str(userId)` (upsert - a reconnect replaces the key rather than creating a second identity), and continues the OAuth flow with that subject.
- **Why:** audit finding A1 - `OAuthStore.subject_for_key` (`sha256(api key)`) was never a real StudyLife identity, just a stable label derived from a credential that can be rotated or shared. The real `AuthUserId` only exists on the StudyLife side; the assertion exchange is how this server learns it without ever seeing a password, and without the user manually copy-pasting an API key into a web form (audit A9 - a key-paste form trains users to paste secrets into whatever page claims to be StudyLife, a phishable pattern).
- **Legacy compatibility, deliberately not migrated:** grants issued before this change have subject = `sha256(key)`. `OAuthStore`/`client_resolver.py` treat `subject` as an opaque string throughout - no code path branches on which shape it is - so old grants keep resolving exactly as before. They are left to expire/be revoked naturally, not backfilled to a `userId` subject.
- **`/connected-apps` is unaffected:** it still re-proves ownership with a raw StudyLife API key (`_validate_studylife_key`, unchanged) rather than the connect flow - it's an internal-only management page, not the public login path this round targeted.
- **Fail-closed fix (audit A14):** `StudyLifeClientResolver.resolve()` previously fell back to the operator's `.env` account for *any* case where `get_access_token()` didn't yield a usable subject - including, in principle, an authenticated HTTP-mode request that somehow reached a tool call without one. Reordered so the `.env` fallback only applies when `self._oauth_store is None` (stdio mode, or HTTP mode not configured at all); once an `OAuthStore` exists, a missing/subjectless token now raises `PermissionError` instead. Defense in depth - the MCP SDK's own auth middleware should already reject an unauthenticated `/mcp` call before any tool runs - not the primary gate.
- **`STUDYLIFE_API_KEY` is now optional at the `Settings` level**, required only for stdio mode (`main()` checks explicitly and raises if unset) - a pure-HTTP deployment with no fallback account no longer needs to configure one just to satisfy pydantic. `StudyLifeClient`/`client_resolver`'s eagerly-constructed default client now tolerates a `None` key (empty headers), since fail-closed means it's genuinely never called in that case.
- **New config `STUDYLIFE_CONNECT_URL`:** StudyLife's own public/browser-facing base URL, distinct from `STUDYLIFE_BASE_URL` (this server's server-to-server target, which may be a cluster-internal address the browser can't reach). Required-for-HTTP-mode the same way `MCP_PUBLIC_URL`/`MCP_TOKEN_ENCRYPTION_KEY` already were - all three now gate whether `server.py` wires up the OAuth provider at all. Committed to `k8s/02-secret.yaml` (placeholder) alongside `MCP_PUBLIC_URL`, same "not secret, but not searchable-in-history either" reasoning as that entry.
- **`k8s/07-tailscale-funnel.yaml`:** `/login` removed from the public path allowlist (nothing redirects there anymore); `/auth/studylife/callback` added (the browser must reach it directly from StudyLife's public redirect - it can't go through the tailnet/LAN-only route).
- **Verified:** `ruff check`, `ruff format --check`, and `mypy --strict src` all clean; `pytest` - 101 tests total (`test_oauth_login_route.py` removed, replaced by `test_oauth_studylife_callback_route.py`: state validation, missing-assertion, happy path with subject/upsert assertions, rejected/network-error exchange with no key material leaked; plus new `client.py` unit tests for `exchange_mcp_assertion`, and new `client_resolver.py` tests for the HTTP-mode fail-closed paths and legacy sha256-subject resolution). Verified against the live StudyLife/studylife-ai counterparts of this shared spec was out of scope for this repo's own change - built and tested against the fixed wire contract, not a live server (the other two implementations were built in parallel by separate efforts against the same spec document).
